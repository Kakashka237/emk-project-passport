### Раздел 2. Процессные протоколы

#### 1. Правила ветвления в Git (GitHub Flow)

- Основная ветка: `main` (всегда стабильна, защищена: прямой push запрещен, каждый релиз помечается тегом `vX.Y.Z`).
- Пример наименования ветки под задачу: `feature/EMK-305-lab-results-fhir` (новый модуль приема результатов анализов из лаборатории).
- Исправление ошибки: `bugfix/EMK-271-department-access-check`.
- Формат имени: `<тип>/<ключ задачи>-<кратко-латиницей>`, тип — `feature`, `bugfix`, `hotfix`, `docs`.
- Сообщение коммита начинается с ключа задачи: `EMK-305 Add FHIR DiagnosticReport mapping`.
- Условие создания Pull Request для нового модуля: модуль собирается без предупреждений, добавлены xUnit-тесты бизнес-логики, контракт `openapi.yaml` обновлен и проходит валидацию, в описании PR указаны задача EMK-xxx и способ проверки.
- Правило слияния: PR одобряется минимум 1 коллегой (для изменений, затрагивающих доступ к ПДн, — дополнительно специалистом по ИБ) после успешного прохождения автоматических тестов и SAST в CI; слияние — squash merge, ветка удаляется.

#### 2. Чек-лист Code Review (3 обязательных пункта)

1. **Защита персональных данных (152-ФЗ, врачебная тайна).** Каждый эндпоинт проверяет роль и отделение пользователя перед выдачей медицинской записи; ФИО, СНИЛС, диагнозы и номера карт не попадают в логи и сообщения об ошибках в открытом виде; SQL-запросы только параметризованные.
2. **Соответствие контракту и модульной структуре.** DTO и коды ответов совпадают со схемами `openapi.yaml`; бизнес-логика в `Emk.Core` не обращается напрямую к HTTP/БД (только через интерфейсы `Emk.Domain`), новые зависимости между проектами не создают циклов.
3. **Тесты и обработка ошибок.** Для новой бизнес-логики есть xUnit-тесты (в т. ч. негативные сценарии: занятый слот, неверный номер карты, недоступная лаборатория); исключения не проглатываются, пользователю показывается понятное сообщение, CI зеленый.

### Раздел 3. Запись архитектурного решения (ADR-001)

**Заголовок:** ADR-001: Выбор стандарта HL7 FHIR R4 для модуля интеграции с лабораториями

**Контекст и проблема:** АИС ЭМК должна получать результаты анализов (общий анализ крови, биохимия) от нескольких лабораторий: собственной лаборатории поликлиники и двух внешних. Каждая лаборатория отдает данные в своем формате (CSV-выгрузка, XML, PDF-бланк), с собственными кодами показателей и единицами измерения. Из-за этого результаты нельзя автоматически привязать к медицинской карте пациента, сравнивать в динамике и проверять на корректность, а подключение новой лаборатории требует отдельной доработки.

**Принятое решение:** Интеграционный шлюз ЭМК принимает результаты только в формате HL7 FHIR R4 (ресурсы `DiagnosticReport` и `Observation`, коды показателей LOINC, единицы UCUM) через защищенный REST API (HTTPS, mTLS, OAuth 2.0). Для лабораторий, не поддерживающих FHIR, на стороне шлюза создается отдельный адаптер-конвертер (паттерн Adapter), который преобразует их формат в FHIR; ядро ЭМК работает только с единой моделью FHIR.

**Отклоненная альтернатива и причина:** Рассматривался прямой обмен файлами с каждой лабораторией в ее собственном формате (CSV/XML по SFTP) с отдельным парсером под каждую. Отклонено, потому что: число парсеров растет вместе с числом лабораторий и каждый меняется при изменении формата партнера; нет единого справочника кодов показателей — невозможно строить динамику анализов; файловый обмен не дает подтверждения доставки и аудита доступа к ПДн, что требуется 152-ФЗ; FHIR является международным стандартом и поддерживается российскими МИС и ЕГИСЗ, что упрощает будущие интеграции.

**Статус:** Принято. **Последствия:** требуется валидация входящих ресурсов по FHIR-профилям и справочник соответствия локальных кодов лабораторий кодам LOINC.
